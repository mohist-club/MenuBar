# Poptro 工程与 UI 标准

本文使用 **必须**、**应该**、**可以** 表示约束强度。新功能、修复和重构都应遵守。

## 1. 运行与身份标准

- 正式使用的 App **必须**位于 `/Applications/Poptro.app`。
- 调试副本、DMG 内副本和正式副本不得同时作为长期运行实例。
- `CFBundleIdentifier`、签名方式或正式安装路径的变化 **必须**按权限迁移处理，不能当成普通重命名。
- 应用 **不得**启用 App Sandbox；当前 AX 读取和模拟按键能力与 Sandbox 冲突。
- App 必须保持 `LSUIElement = true`，避免无意义的 Dock 图标。

## 2. 权限标准

- 启动、热键触发和翻译流程只能静默调用 `AXIsProcessTrusted()`。
- 只有用户点击“前往系统设置授权”等显式操作时，才可以使用
  `AXIsProcessTrustedWithOptions(...prompt: true)`。
- 未授权不能阻止快捷键注册；无选中文字时应降级为手动输入。
- 权限文案必须显示当前实际运行路径，便于识别是否授权了错误副本。
- 不得通过循环弹框或重复打开系统设置“强制”用户授权。

## 3. 快捷键标准

- 内置翻译快捷键使用稳定名称 `translateSelection`，默认 `Command + G`。
- 应用快捷键名称必须由持久化 UUID 生成，不能由可变应用名或路径直接生成。
- 录制快捷键时不得触发它所绑定的业务动作。
- 保存、删除、启用或停用快捷键后，必须同步更新全局监听。
- 快捷键冲突要在录制阶段给出明确反馈；不得静默失败。
- 翻译快捷键与“打开设置”必须是两条独立事件链。

## 4. 划词标准

- 取词顺序固定为：AX Selected Text → 模拟 `Command + C` → 手动输入。
- 剪贴板兜底前必须备份所有类型的数据，不仅是纯文本。
- 只有 `changeCount` 发生变化时才读取新剪贴板文本，避免使用旧内容。
- 读取完成后必须恢复用户剪贴板。
- 延迟值必须通过真实应用验证；修改当前 120ms 前应覆盖原生 App、浏览器和 Electron App。
- 取词失败不是崩溃条件，也不应自动打开整个设置窗口。

## 5. 翻译流程标准

- `TranslationFlowCoordinator` 是翻译流程的唯一编排入口。
- 每次请求必须分配新的 ID，所有 token 和完成回调都必须校验当前 ID。
- 切换服务、语言或清空内容时，旧请求不得继续写入 UI。
- 翻译方向由运行时代码明确指定；系统 Prompt 不得再包含相互冲突的方向判断指令。
- 快速服务切换菜单只展示配置完整且当前可用的服务。
- 服务错误要转成用户可理解的信息；网络瞬断、超时和 DNS 波动允许有限重试，不得无限重试。
- 测速请求必须使用短文本并提示会消耗少量额度。

## 6. 数据和隐私标准

- 仓库中严禁出现真实 API Key、个人应用绑定、私人文件路径、账号、邮箱或剪贴板内容。
- API Key 只能在用户明确保存时持久化，日志中不得输出完整 Key。
- 普通设置放入 `Application Support/Poptro`，不得散落在项目目录。
- 新配置字段必须向后兼容：使用 `decodeIfPresent`，给出稳定默认值，并增加迁移测试。
- 删除或更名存储键之前必须提供迁移方案。
- 诊断信息默认不得包含原文、译文和 API Key。
- 文档必须明确：本机 AES-GCM 存储避免明文落盘，但不等同于硬件安全模块。

## 7. macOS 原生 UI 标准

### 7.1 窗口与结构

- 设置页使用系统原生左右导航结构，外观跟随通用设置。
- 翻译窗口默认尺寸为 `940 × 580`，最小 `740 × 460`，最大 `1400 × 1000`。
- 窗口必须允许拖动、缩放，并把恢复后的 frame 限制在当前可见屏幕内。
- 四角使用同一 continuous corner radius；外层裁切、描边和 HostingView 圆角必须一致。
- 标题栏只显示单色 Poptro 标识、名称和必要的 Google AI 动作。

### 7.2 排版

- 原文和译文使用系统字体，正文基准为 16pt、regular、4pt 附加行距。
- 正文使用动态语义文字色并轻微降低强度，不使用纯黑或纯白硬编码。
- 标签与辅助信息使用 10.5–12pt，最多使用 regular / medium / semibold 三档中的必要两档。
- 空状态和错误说明使用 14pt，不得与正文争夺层级。

### 7.3 材质与颜色

- macOS 26+ 优先使用系统 Liquid Glass；旧系统使用 `NSVisualEffectView`。
- 玻璃只负责窗口材质，正文阅读区必须有中性底层以保证对比度。
- 浅色、深色都使用系统语义色，不能为单一模式写死 RGB 文本色。
- 控件采用轻量 `controlBackgroundColor` 和低对比描边；避免多个高对比实心按钮。
- 图标使用 SF Symbols 单色模板，不混用彩色装饰图标。

### 7.4 滚动与控件

- 原文和译文必须使用一致的原生文本排版和选择行为。
- 文本滚动区必须强制使用 overlay scroller，不能继承系统“始终显示滚动条”的宽轨样式。
- overlay 约束必须在控件挂载到窗口后仍然有效；只在初始化阶段赋值不够。
- 图标按钮需要帮助提示；禁用状态必须清晰但不能破坏布局尺寸。
- 底部仅保留已配置服务、复制和重置，不增加无业务价值的装饰状态。

## 8. 生命周期与并发标准

- 设置窗口应复用同一 `NSWindow`，关闭后不能因释放错误导致再次打开崩溃。
- 对窗口、面板和异步任务的回调优先使用弱引用，避免循环持有。
- UI 状态更新必须回到主线程。
- 窗口关闭、重置或开始新翻译时必须使旧请求失效。
- 主线程不得执行网络阻塞、长时间 sleep 或模型推理。

## 9. 测试标准

每次提交至少执行：

```bash
swift test
swift build -c release
```

以下改动必须增加或更新测试：

- Codable 字段、默认值或迁移逻辑。
- 语言识别和目标语言选择。
- 服务模型路由、已配置服务过滤、测速错误分类。
- 面板能否渲染、原生滚动条模式、关键字号等容易回归的 UI 行为。

涉及 AX、TCC、全局快捷键、DMG 安装或多屏幕的行为还必须做真机手工测试。

## 10. 文档与提交标准

- 功能、配置、发布方式变化时必须同步相关 Markdown。
- 代码注释优先解释系统限制和设计原因，不重复代码字面含义。
- Commit 聚焦单一主题，使用清楚的祈使式英文标题。
- 发布提交不得夹带临时截图、个人设计草稿或本机产物。
